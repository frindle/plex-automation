# plex-automation

Webhook-driven automation for Sonarr/Radarr + Deluge, deployed as a Docker container on Unraid.

## What it does

`arr-webhook.py` runs a Flask app (port `9876`) that Sonarr and Radarr call via their notification webhooks:

- **On Grab**: if the grab is a quality upgrade and the release is over 10GB, labels the new torrent in Deluge so it can be throttled/tracked separately instead of competing with normal downloads. Once it is in that lane the queue dupe pass runs immediately, scoped to just that movie/series, so a second in-flight release of the same thing is resolved in seconds rather than waiting for the daily sweep.
- **On Download (import) of an upgrade**: finds the old torrent that the new file replaced and either deletes it immediately (PROPER/REPACK) or labels it `superseded` and moves it to a seeding directory.

Background schedulers (run inside the same process):
- **Daily**: removes `superseded` torrents that have seeded past `SEED_DAYS` (default 21), and dedupes Radarr's and Sonarr's downloads (this and the weekly run are the unscoped backstop behind the grab-time pass, covering missed webhooks and grabs that happened while the service was down) (Radarr: highest custom-format-score entry per movie; Sonarr: best covering release per overlapping episode set — both across the *arr's own queue and the throttled `radarr-upgrade`/`sonarr-upgrade` lane, which that queue cannot see).
- **Hourly**: bumps normal `sonarr`/`radarr`-labeled torrents to the top of the Deluge queue.
- **Monthly (1st of month)**: purges stalled upgrade torrents, triggers a Radarr bulk search to catch missed upgrades, waits, then relabels/requeues anything that came in as a result.

`monthly_upgrade.py` is a standalone script duplicating the monthly cycle (purge → bulk search → wait 90 min → relabel/requeue), kept for manual or cron-triggered runs independent of the long-running webhook process.

`media_share.py` adds a friend-facing media upload portal (Flask blueprint, registered into the same app/port) at `/share`:
- Friends authenticate via Cloudflare Access (the app trusts the `Cf-Access-Authenticated-User-Email` header, so it must only be reachable through the Cloudflare Tunnel — never expose this port directly to the internet).
- Browse the read-only-mounted Movies/TV Shows/Music libraries and upload a file or whole folder to that friend's own SFTP server, looked up by their authenticated email in `FRIENDS_CONFIG`.
- Uploads run in a background thread, throttled to `UPLOAD_RATE_LIMIT_MBIT` (default 5 Mbit/s) so a large upload doesn't saturate the connection.
- Every upload is logged to a SQLite DB (`/data/share_uploads.db`); `/share/usage` shows each friend their own bandwidth usage over the last 7/30/60/90/182/365 days.

## Setup

1. Copy `.env.example` to `.env` and fill in:
   - `DELUGE_PASSWORD`
   - `SONARR_API_KEY`
   - `RADARR_API_KEY`
   - `FRIENDS_CONFIG` (JSON map of Cloudflare Access email → SFTP destination) if using the media share portal
2. Adjust the hardcoded Deluge/Sonarr/Radarr URLs, labels, `SEED_DAYS`, `SEEDING_DIR`, and the `/mnt/Media/...` library volume mounts directly in `docker-compose.yml` if your setup differs.
3. Build and run:
   ```
   docker-compose build && docker-compose up -d
   ```
4. Point Sonarr/Radarr's webhook connections (Settings → Connect) at `http://<container-ip>:9876/webhook/sonarr` and `/webhook/radarr`, enabling the **On Grab** and **On Import** (upgrade) triggers.
5. If using the media share portal, point a Cloudflare Tunnel + Access application at `http://<container-ip>:9876/share` and restrict ingress so the container is only reachable through the tunnel.

## LLM decisions

Advisory decisions for upgrade grabs, import identity and duplicate keepers (`llm_decide.py`, `llm_advisor.py`). `LLM_DECISIONS=off` (default) never calls a model; `shadow` logs what the chain would do next to what the rules did; `enforce` lets a confident answer (>= 0.75) override the rules. Hard rules always win. Set values in `.env`; compose passes them through with empty defaults.

Layers, each skipped when its env is unset:

0. Unraid Ollama (free, tried first): `UNRAID_OLLAMA_URL` (e.g. `http://<host>:11434`), `LLM_UNRAID_MODEL` (default `qwen3:14b`; fixed, never auto-picked), `LLM_UNRAID_KINDS` (default `import_identity`, comma-separated). Native `/api/chat`, no thinking, connect 2 s / total 30 s (covers a cold load). Asked only when `/api/ps` shows nothing loaded or its own model loaded (another resident model means the queue has the GPU), and when the optional `LLM_UNRAID_HOLD_URL` + `LLM_UNRAID_HOLD_TOKEN` check isn't holding (same contract as the local hold). Its answer counts only when, after hard rules, it is decisive (`match`/`mismatch`) at confidence >= 0.75; anything else (unsure, weak, unparseable, timeout, skipped) passes on to local Darkbloom, never straight to Claude, and doesn't start the pending clock. Each decision log row carries `unraid: {model, latency_ms, pass}` where `pass` is null when Unraid settled it, else `other-model-resident`, `hold`, `timeout`, `error`, `unparseable`, `unsure` or `weak`. Skips never alert.
1. Local Darkbloom: `DARKBLOOM_BASE_URL` + `DARKBLOOM_API_KEY` (OpenAI-compatible). Model is `LLM_LOCAL_MODEL`, else the first id from `/v1/models` (cached 10 min). `LLM_DECIDE_URL`/`LLM_DECIDE_MODEL`/`LLM_DECIDE_KEY` still work when `DARKBLOOM_BASE_URL` is unset. Optional hold check: `LLM_LOCAL_HOLD_URL` + `LLM_LOCAL_HOLD_TOKEN`; the local layer is skipped only when the response is 200 with top-level `hold: true` (errors fail open).
2. Paid Darkbloom: `DARKBLOOM_CLOUD_API_KEY`, `DARKBLOOM_CLOUD_MODEL` (default `qwen3.5-35b-a3b`).
3. Claude: `ANTHROPIC_API_KEY`, `LLM_CLAUDE_MODEL` (default `claude-sonnet-5-5`), structured output via the `anthropic` SDK.
4. Rules: an exhausted chain returns nothing and the rules action stands.

Waiting for local: when the local layer is unavailable (down, timeout, bad output, hold) the decision is pending for `LLM_LOCAL_WAIT_MIN` minutes (default 15) before any paid layer is used. Pending state is kept in `LLM_PENDING_PATH` (`/data/llm_pending.json`, keyed by kind + hash of the facts) so a restart keeps the clock; entries drop on resolve or after 24 h. While pending: import identity answers `unsure` (enforce) and dupe keeper `keep_both`; shadow keeps the rules action. An upgrade grab applies the rules action at once and a background thread retries local about every 60 s, then escalates; a late `reject` removes the torrent and a late `throttle` labels it (enforce only). A restart drops pending grabs and the rules action stands. A valid but low-confidence open-model answer goes to Claude immediately.

Logging: each row in `LLM_DECISIONS_LOG` carries `layer`, `model`, `latency_ms`, `pending_min`, and for paid calls `paid_calls` (token usage and provider request id). Keys and headers are never logged. Each escalation to a paid layer adds an activity line (`llm-escalation`). `GET /llm-decisions` reads the log; `GET /llm-spend?month=YYYY-MM` sums calls and tokens per paid layer (tokens only, no prices).

## Deployment

Runs on Unraid at `/mnt/user/appdata/plex-automation`, on the `br0` macvlan network (external) at a static IP. `.env` lives only on the server and is gitignored — never commit real secrets.

## CI

GitHub Actions (`.github/workflows/ci.yml`) runs on every push/PR to `main`: syntax + `ruff` lint check on all Python scripts, then a Docker build to make sure the image actually builds.

- Fix the supersede workflow leaving 0%/paused "superseded" orphans (the pile seen after a reboot recheck). `supersede_torrent()` called `core.move_storage` *after* the *arr upgrade import had already deleted/overwritten the old file, so a fileless torrent was relocated to `SEEDING_DIR` where it sat at 0% forever — never accruing `seeding_time`, so `cleanup_superseded` (gated on the seed window) could never reap it. Two fail-safe guards: `supersede_torrent` now probes `total_done` (new `_torrent_has_local_data`) and only moves when data is actually present, else it labels the torrent superseded but skips the move and records `supersede-no-data`; and `cleanup_superseded` gained an orphan reaper that removes a 0%-no-data superseded torrent with `remove_data=False` (a true orphan has no files to leave; a mount-race false 0% can't delete real bytes), gated on a `mount_healthy` check so the shfs mount-race signature — every torrent reading 0% — can never trigger mass removal. The primary data-preservation fix is the *arr config already applied (Use Hardlinks + Completed Download Handling Remove=No), which keeps the download inode alive through import; these guards make the automation self-healing when that slips. New `test_supersede_orphan.py`.
- Dedupe throttled upgrades at **grab time** instead of only on the daily/weekly sweep. `handle_grab()` relabels a throttled upgrade out of the *arr's own download-client category, which is what blinds the *arr's `QueueSpecification` and lets it grab a second release of the same film — the scheduled passes did catch that, but the duplicate could burn bandwidth for up to a day first. New `dedupe_grabbed_release()` runs the existing pass immediately, scoped to the one movie/series just grabbed, so the second copy is dropped before it has really started. It is called **after** the relabel + `queue_bottom`, which is the earliest point the new torrent is observable to the pass at all (the pass looks in the `-upgrade` lane; while the *arr's queue record is still stale-visible the existing `queue_hashes` check stops it being counted twice). The remaining race is the *arr's own history — the Grab webhook can beat the `grabbed` record being queryable by `downloadId` — so the identity is **polled** for (`GRAB_DEDUPE_TRIES`, default 6, `GRAB_DEDUPE_DELAY`s apart, default 5) rather than slept on, and if it never resolves nothing is touched. Implemented by giving `cleanup_radarr_queue_dupes(movie_id=None)` / `cleanup_sonarr_queue_dupes(series_id=None)` an optional scope rather than writing a second copy of the logic; scoping narrows what is *compared*, not what is read, and every safety property is unchanged — Sonarr in particular still keeps its episode-**set** identity with subset-only elimination inside the series, so a different episode of the same series is never removed. Both passes now run under a shared reentrant lock, since two Grab webhooks for the same movie arrive on separate threads seconds apart and interleaved passes reading either side of a write could otherwise pick different keepers and remove both copies. The daily and weekly schedulers are unchanged and remain the backstop. New `test_grab_dedupe.py`.
- Add the Sonarr counterpart of the queue dupe pass, which never existed: `cleanup_sonarr_queue_dupes()`. Sonarr has the identical blind spot (`Deluge.GetItems()` → `GetTorrentsByLabel(TvCategory)`), so a throttled `sonarr-upgrade` torrent leaves `/api/v3/queue` the moment `handle_grab()` relabels it — and unlike Radarr, nothing was policing that population from either side. Candidate set is the Sonarr queue plus the in-flight throttled lane, identity for lane torrents coming from `/api/v3/history?downloadId=`. Identity is where the two services differ: a movie is one `movieId`, but a TV grab covers a *set* of episodes (single episode, multi-episode file, or season pack), so `seriesId` is not an identity — two different episodes of one series are not duplicates. Sonarr also emits one queue record *per episode*, so a season pack's records are folded back into a single candidate before anything is compared. A candidate is dropped only when its episode set is a **subset** of a keeper's, so the keeper delivers everything the loser would; keepers are chosen by coverage first (dropping a 10-episode pack to keep one higher-scoring episode inside it would leave nine episodes with nothing in flight), then custom-format score, then bytes already pulled. Straddling packs (`S01E01-05` vs `S01E04-10`) are both kept. Same safety properties as the Radarr pass: finished/seeding torrents are never touched, queue-record losers go through the queue API with `blocklist: False` (bulk endpoint, since a pack is many records), lane losers are relabeled `superseded` for `cleanup_superseded`, and each removal is individually wrapped. Runs on the same daily and weekly schedulers as the Radarr pass. New `test_sonarr_queue_dupes.py`.

(The same blind spot defeats Radarr's own `QueueSpecification`, which is why the second release gets grabbed at all.)
