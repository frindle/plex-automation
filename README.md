# plex-automation

Webhook-driven automation for Sonarr/Radarr + Deluge, deployed as a Docker container on Unraid.

## What it does

`arr-webhook.py` runs a Flask app (port `9876`) that Sonarr and Radarr call via their notification webhooks:

- **On Grab**: if the grab is a quality upgrade and the release is over 10GB, labels the new torrent in Deluge so it can be throttled/tracked separately instead of competing with normal downloads. Once it is in that lane the queue dupe pass runs immediately, scoped to just that movie/series, so a second in-flight release of the same thing is resolved in seconds rather than waiting for the daily sweep.
- **On Download (import) of an upgrade**: finds the old torrent that the new file replaced and either deletes it immediately (PROPER/REPACK) or labels it `superseded` and moves it to a seeding directory.

Background schedulers (run inside the same process):
- **Daily**: removes `superseded` torrents that have seeded past `SEED_DAYS` (default 21), and dedupes Radarr's and Sonarr's downloads (this and the weekly run are the unscoped backstop behind the grab-time pass, covering missed webhooks and grabs that happened while the service was down) (Radarr: highest custom-format-score entry per movie; Sonarr: best covering release per overlapping episode set — both across the *arr's own queue and the throttled `radarr-upgrade`/`sonarr-upgrade` lane, which that queue cannot see).
- **Hourly**: trims the upgrade lane to `UPGRADE_LANE_MAX` (see **Deluge trimming**), then bumps normal `sonarr`/`radarr`-labeled torrents to the top of the Deluge queue.
- **Daily**: retires long-seeded torrents (see **Deluge trimming**).
- **Monthly (1st of month)**: purges stalled upgrade torrents, triggers a Radarr bulk search to catch missed upgrades, waits, then relabels/requeues anything that came in as a result.

`monthly_upgrade.py` is a standalone script duplicating the monthly cycle (purge → bulk search → wait 90 min → relabel/requeue), kept for manual or cron-triggered runs independent of the long-running webhook process.

`media_share.py` adds a friend-facing media upload portal (Flask blueprint, registered into the same app/port) at `/share`:
- Friends authenticate via Cloudflare Access (the app trusts the `Cf-Access-Authenticated-User-Email` header, so it must only be reachable through the Cloudflare Tunnel — never expose this port directly to the internet).
- Browse the read-only-mounted Movies/TV Shows/Music libraries and upload a file or whole folder to that friend's own SFTP server, looked up by their authenticated email in `FRIENDS_CONFIG`.
- Uploads run in a background thread, throttled to `UPLOAD_RATE_LIMIT_MBIT` (default 5 Mbit/s) so a large upload doesn't saturate the connection.
- Every upload is logged to a SQLite DB (`/data/share_uploads.db`); `/share/usage` shows each friend their own bandwidth usage over the last 7/30/60/90/182/365 days.

## Setup

1. Copy `.env.example` to `.env` and fill in:
   - `DELUGE_PASSWORD`
   - `SONARR_API_KEY`
   - `RADARR_API_KEY`
   - `FRIENDS_CONFIG` (JSON map of Cloudflare Access email → SFTP destination) if using the media share portal
2. Adjust the hardcoded Deluge/Sonarr/Radarr URLs, labels, `SEED_DAYS`, `SEEDING_DIR`, and the `/mnt/Media/...` library volume mounts directly in `docker-compose.yml` if your setup differs.
3. Build and run:
   ```
   docker-compose build && docker-compose up -d
   ```
4. Point Sonarr/Radarr's webhook connections (Settings → Connect) at `http://<container-ip>:9876/webhook/sonarr` and `/webhook/radarr`, enabling the **On Grab** and **On Import** (upgrade) triggers.
5. If using the media share portal, point a Cloudflare Tunnel + Access application at `http://<container-ip>:9876/share` and restrict ingress so the container is only reachable through the tunnel.

## LLM decisions

Advisory decisions for upgrade grabs, import identity and duplicate keepers (`llm_decide.py`, `llm_advisor.py`). `LLM_DECISIONS=off` (default) never calls a model; `shadow` logs what the chain would do next to what the rules did; `enforce` lets a confident answer (>= 0.75) override the rules. Hard rules always win. `LLM_MODE_<KIND>` (`LLM_MODE_IMPORT_IDENTITY`, `LLM_MODE_DUPE_CONFIRM`, `LLM_MODE_UPGRADE_GATE`) sets one kind on its own, so one kind can enforce while the others stay in shadow; empty follows `LLM_DECISIONS`, and `LLM_DECISIONS=off` turns every kind off. `/llm-layers` shows each kind's mode under `modes`. Set values in `.env`; compose passes them through with empty defaults.

`GET /llm-stats?days=N` (default 7, 1..90) reports per kind how many questions were answered, by which layer, why the rest were not (cold_load_timeout, warm_timeout, other_model_loaded, plex_holding_gpu, backoff, layer_down, no_layer, unparseable, other), hard-rule vetoes and agreement, with `below_target` flags (answered < 90%, a cause > 5%, agree < 95%, any veto); kinds below target also show on `/digest`.
`torrent_error` (`LLM_MODE_TORRENT_ERROR`) is shadow-only: after the Deluge error repair hands a torrent to a person (partial, library-error, missing, library-match, relink-candidate) the model picks recheck, resume, relink, wait, remove_and_research or ask from facts alone, and the answer is only logged (never acted on, even in enforce). `TORRENT_ERROR_LLM_MAX` (default 10) caps new questions per run; answers are cached 24 h. `backtest_torrent_error.py` replays JSONL fact rows against a model endpoint.
`unregistered_triage` (`LLM_MODE_UNREGISTERED_TRIAGE`, free layers only, shadow-only for now): for each torrent the unregistered sweep finds, the model picks keep / remove_keep_library / remove_and_research / ask from counts and classes (no names or paths) and the answer is only logged next to the rules' action; the rules still decide, the mass-outage guard is never put to the model, at most `UNREGISTERED_LLM_MAX` (default 10) new questions per sweep, answers cached 24 h.
`stuck_import` (`LLM_MODE_STUCK_IMPORT`, free layers only, shadow-only): when an importBlocked download still needs a person after the auto-import rescue, the model picks wait / retry_import / ask from classes and an age (no names) and the answer is only logged next to the rules' action (ask); the notification is sent as before. At most `STUCK_IMPORT_LLM_MAX` (default 10) new questions per pass, answers cached 24 h. `backtest_stuck_import.py` replays JSONL fact rows.
`stuck_upgrade_tag` (`LLM_MODE_STUCK_UPGRADE_TAG`, free layers only, shadow-only): when an upgrade import finds no torrent for its download id (the "upgrade tag may be stuck" notification), the model picks wait / run_sweep / ask from counts and flags (no names) and the answer is only logged next to the rules' action (ask); the notification is sent as before. Answers cached 24 h. `backtest_stuck_upgrade_tag.py` replays JSONL fact rows.
`duplicate_folder` (`LLM_MODE_DUPLICATE_FOLDER`, free layers only, shadow-only): for each new duplicate-media-folder finding the model picks leave / merge / ask from counts, sizes and suffix classes (no folder names) and the answer is only logged next to the rules' action (ask); the digest line is written as before and nothing is moved. At most `DUPLICATE_FOLDER_LLM_MAX` (default 10) new questions per scan, cached 24 h. `backtest_duplicate_folder.py` replays JSONL fact rows.
`audit_findings` (`LLM_MODE_AUDIT_FINDINGS`, free layers only, shadow-only): for each newly reported finding of the library seed audit and the downloads audit, the model picks fix / ignore / ask from classes, counts and sizes (no torrent names or paths) and the answer is only logged next to the rules' action (ask); the audit notice is sent as before and nothing is changed. `fix` is turned into ask when the follow-up is human-only (a delete, move or relabel of library files) and `ignore` into ask when ignoring could lose library data (both fail closed on a missing flag). At most `AUDIT_FINDINGS_LLM_MAX` (default 10) new questions per audit run, cached 24 h. `backtest_audit_findings.py` replays JSONL fact rows.
`arr_health` (`LLM_MODE_ARR_HEALTH`, free layers only, shadow-only): before each Sonarr/Radarr health push (a sustained outage, its recovery, a series or movie removed from its metadata site) the model picks notify / hold / self_heals from the event, service, check name and minutes (no titles, hostnames or URLs) and the answer is only logged next to the rules' action (notify); the push is sent as before. Hard floor: an outage at or past `OUTAGE_ALERT_MIN` is always notify, and a missing duration counts as past it. Fallback is notify. At most `ARR_HEALTH_LLM_MAX` (default 10) new questions per tick, cached 24 h. `backtest_arr_health.py` replays JSONL fact rows.
Both new kinds are opt-in: they stay off until their own `LLM_MODE_<KIND>` is set, whatever `LLM_DECISIONS` says, so a deploy never starts them before their back-test. Their questions are asked on a background thread after the repair or sweep finishes, one batch per kind at a time, so a cold model never delays the rules.

Layers, each skipped when its env is unset:

0. Unraid Ollama (free, tried first): `UNRAID_OLLAMA_URL` (e.g. `http://<host>:11434`), `LLM_UNRAID_MODEL` (default `qwen3:14b`; fixed, never auto-picked), `LLM_UNRAID_KINDS` (default `import_identity,dupe_confirm,upgrade_gate`, comma-separated). Native `/api/chat`, no thinking, connect 2 s / total 30 s; when the model is cold (nothing loaded in `/api/ps`, or listed but it hasn't answered this process in the last 5 min: a listing can be a load still running or just aborted), import identity (asked from the background poller) waits `LLM_UNRAID_COLD_TIMEOUT` (default 240 s) so the load fits, while grab-time kinds keep 30 s. After a timeout the layer is skipped for `LLM_UNRAID_BACKOFF_MIN` (default 15) minutes, doubling per timeout in a row up to 60 (an answer resets it; `0` turns it off), because each timed-out ask had started a model load that the hang-up aborted. Asked only when `/api/ps` shows nothing loaded or its own model loaded (another resident model means the queue has the GPU), and when the optional `LLM_UNRAID_HOLD_URL` + `LLM_UNRAID_HOLD_TOKEN` check isn't holding (same contract as the local hold; the queue serves it at `/api/gpu-hold?lane=unraid`). When Unraid is the only free layer, a hold whose cause is `plex` keeps the decision pending past the paid clock (playback ends; the next run asks Unraid again); other holds count like any other miss. Its answer counts only when, after hard rules, it is decisive (`match`/`mismatch`) at confidence >= 0.75; anything else (unsure, weak, unparseable, timeout, skipped) passes on to local Darkbloom, never straight to Claude, and doesn't start the pending clock (when Unraid is the only free layer, its misses start the same pending clock local uses). Each decision log row carries `unraid: {model, latency_ms, pass}` (plus `hold_cause` on a hold that names one) where `pass` is null when Unraid settled it, else `backoff`, `other-model-resident`, `hold`, `timeout`, `error`, `unparseable`, `unsure` or `weak`. Skips never alert.
1. Local Darkbloom: `DARKBLOOM_BASE_URL` + `DARKBLOOM_API_KEY` (OpenAI-compatible). The rule is **never a switch**: plex uses whatever Darkbloom has loaded and never causes a model to be loaded or swapped. It reads every id from `/v1/models` (cached 15 s; the list is what is loaded, and an entry marked `loaded: false` or an unloaded `status` would be ignored) and, per kind, uses the first listed id whose back-test passed for that kind (`LLM_LOCAL_APPROVED_<KIND>`, comma-separated, `*` = any). Defaults: `qwen3.5-35b-a3b` for `import_identity` and `upgrade_gate`; every other kind is empty until its Studio back-test passes (`backtest_local.py`). Skip reasons (the layer sits out like a hold: pending clock, log `local_skip`): `model-not-approved` (loaded, but none approved for this kind), `model-unknown` (`/v1/models` unreadable or empty), `model-not-loaded` (the pin is not listed). `LLM_LOCAL_MODEL` pins one model for every kind (bypasses the approved list) but it must be among the listed ids, otherwise the layer is skipped; a pin can never make Darkbloom load a model. `LLM_DECIDE_URL`/`LLM_DECIDE_MODEL`/`LLM_DECIDE_KEY` still work when `DARKBLOOM_BASE_URL` is unset. `/llm-layers` has a `local_now` block: the loaded ids and, per kind, the model it would use now or why it is skipped. Optional hold check: `LLM_LOCAL_HOLD_URL` + `LLM_LOCAL_HOLD_TOKEN`; the local layer is skipped only when the response is 200 with top-level `hold: true` (errors fail open).

Approved-model variables, one per kind (all kinds, an empty value means the default above): `LLM_LOCAL_APPROVED_IMPORT_IDENTITY`, `LLM_LOCAL_APPROVED_UPGRADE_GATE`, `LLM_LOCAL_APPROVED_DUPE_CONFIRM`, `LLM_LOCAL_APPROVED_TORRENT_ERROR`, `LLM_LOCAL_APPROVED_UNREGISTERED_TRIAGE`, `LLM_LOCAL_APPROVED_STUCK_IMPORT`, `LLM_LOCAL_APPROVED_STUCK_UPGRADE_TAG`, `LLM_LOCAL_APPROVED_DUPLICATE_FOLDER`, `LLM_LOCAL_APPROVED_AUDIT_FINDINGS`, `LLM_LOCAL_APPROVED_ARR_HEALTH`.
2. Paid Darkbloom (backup only): `DARKBLOOM_CLOUD_API_KEY`, `DARKBLOOM_CLOUD_MODEL` (default `qwen3.5-35b-a3b`). Asked with thinking off and 2048 max tokens (with thinking on, every answer used the whole budget reasoning and was unparseable); if the server rejects `chat_template_kwargs` it is asked once more without it.
3. Claude: `ANTHROPIC_API_KEY`, `LLM_CLAUDE_MODEL` (default `claude-sonnet-5-5`), structured output via the `anthropic` SDK.
4. Rules: an exhausted chain returns nothing and the rules action stands.

Paid only as backup: with no free layer (Unraid or local) configured, no paid layer or Claude is asked and the rules stand (log `error: no free layer configured`). Waiting for local: when the local layer is unavailable (down, timeout, bad output, hold) the decision is pending for `LLM_LOCAL_WAIT_MIN` minutes (default 15) before any paid layer is used. Pending state is kept in `LLM_PENDING_PATH` (`/data/llm_pending.json`, keyed by kind + hash of the facts) so a restart keeps the clock; entries drop on resolve or after 24 h. While pending: import identity answers `unsure` (enforce) and dupe keeper `keep_both`; shadow keeps the rules action. An upgrade grab applies the rules action at once and a background thread retries local about every 60 s, then escalates; a late `reject` removes the torrent and a late `throttle` labels it (enforce only). A restart drops pending grabs and the rules action stands. A valid but low-confidence open-model answer goes to Claude immediately.

Grab-time identity check: every grab (new and upgrade, Sonarr and Radarr) is compared with the series/movie it was grabbed for, in a background thread (alert-only; nothing is removed, blocked or relabelled). Hard rules run first; if they flag it, the series' alternate titles (Radarr: alternative and original titles) are fetched and any one that passes clears it. The model is asked in the current `LLM_DECISIONS` mode (none when `off`). Tiers: hard-rule flag and the model did not say `match` (mismatch, unsure, pending or off) sends a Pushover "Possible wrong match" plus an `identity-grab` activity line; a flag the model calls `match`, or a model `mismatch` with clean rules, is an activity line only. One alert per downloadId per 24 h. `GRAB_IDENTITY_CHECK=0` disables it (default `1`).

Logging: each row in `LLM_DECISIONS_LOG` carries `layer`, `model`, `latency_ms`, `pending_min`, and for paid calls `paid_calls` (token usage and provider request id). Keys and headers are never logged. Each escalation to a paid layer adds an activity line (`llm-escalation`). `GET /llm-decisions` reads the log; `GET /llm-spend?month=YYYY-MM` sums calls and tokens per paid layer (tokens only, no prices).

## Arr health

`arr_health.py`, run from a background thread every `ARR_HEALTH_INTERVAL` seconds (300):

- **Outages**: Sonarr/Radarr not answering, their indexer, download-client and root-folder health checks, and Deluge not answering. One Pushover after 30 minutes down, one more on recovery. Short blips never push; an outage not seen for 30 minutes (e.g. the container was off) starts its clock again.
- **Removed from TheTVDB / TMDb**: the removed-series/movie health checks. The first read per arr is a silent baseline; each newly removed item pushes once.
- **Broken library files**: every `ARR_BROKEN_INTERVAL` seconds (21600), the arrs' error logs are read for "Unable to parse media info from file". Each file still lacking media info is rescanned, then confirmed on a pass at least an hour later. Files changed in the last hour are left alone (may still be copying), files that read fine again are dropped, and a file is only looked at again after a newer error. With `ARR_HEALTH_APPLY=1` (off by default) a confirmed file's source torrent is force-rechecked in Deluge when Deluge still has it; otherwise, or if the recheck didn't fix it, the file is deleted through the arr and a search is started. Unmonitored items are never deleted, at most 3 are replaced per pass, and more than 5 broken at once changes nothing and pushes once (looks like a mount or ffprobe problem). Without apply, `/digest` shows what apply would do for each file.

State: `ARR_HEALTH_STATE` (`/data/arr_health_state.json`). Outages and broken files also show in `/digest` and the activity log (`arr-health`).

## Deluge trimming

`deluge_trim.py` (pure planners), wired in `arr-webhook.py`:

- **Upgrade-lane cap** (`UPGRADE_LANE_MAX`, default 10 = Deluge's active-download slots, `0` = off). The lane is every unfinished torrent labeled `radarr-upgrade`, `sonarr-upgrade` or their `-recent` variants. Anything that has downloaded a byte (or whose progress Deluge can't report) is always kept, even over the cap. Untouched torrents (0 bytes) are kept in run order (already in a download slot, then `-recent`, then Deluge queue position, then oldest) until the lane holds the cap; the rest are removed from Deluge with their (empty) files left alone. Runs hourly, right after the monthly cycle's relabel, and on each throttled upgrade grab (a grab landing in a full lane is dropped at once). The upgrade search is a refill, not a standing queue: it skips its poll while the lane is full (or Deluge can't report it), and otherwise searches at most as many items as there are free slots, so each finished upgrade makes room for the next one. Radarr/Sonarr find dropped upgrades again on later searches. Preview: `GET /upgrade-lane-cap`; trim now: `POST /upgrade-lane-cap?apply=1`.
- **Seed retirement** (`SEED_RETIRE_DAYS`, default 180, `0` = off). Finished torrents labeled `sonarr`, `radarr`, `lidarr`, `library-seed` or an upgrade label (`SEED_RETIRE_LABELS` overrides) that have seeded at least that many days in a swarm with more than `SEED_RETIRE_MIN_SWARM` (5) other seeds stop seeding, longest-seeded first, at most `SEED_RETIRE_PER_RUN` (100) a day. **Idle rule** (`SEED_IDLE_DAYS`, default 14, `0` = off): a torrent on those labels that has uploaded nothing for that many days (Deluge's `time_since_upload`; never uploaded counts as idle, unknown never does) retires once it has seeded `SEED_IDLE_MIN_DAYS` (default and minimum `SEED_DAYS`, 21), so quiet seeds go early and ones still uploading keep seeding until `SEED_RETIRE_DAYS`. Same swarm rule; aged-out torrents go first, then the longest idle. The preview shows each candidate's `rule`, `idle_days` and `ratio`. The download copy is deleted only when the library verifiably holds every video; `library-seed` torrents always keep their files. When files are kept (here or in any other keep-data removal), the torrent's own samples and release clutter (`.nfo`, `.txt`, `.sfv`, `.srr`, links, Proof/Screens pictures: `episode_retention.is_junk`) are deleted right after the entry goes, leaving videos, subtitles and artwork; nothing is deleted for a cross-seed still loaded, a torrent with no main video, or a junk file over 50 MB. Unlabeled and other labels are never touched. `remove_torrent`'s `SEED_DAYS` floor still applies. Preview: `GET /retire-seeds`; one batch now: `POST /retire-seeds?apply=1`.

Both record a `cleanup` line in the activity log when they remove anything.

## Stuck downloads

`stuck_plan.py` (pure planner), wired in `arr-webhook.py`. Every `STUCK_CHECK_INTERVAL` seconds (default 600) it looks at unfinished torrents with a normal `sonarr` or `radarr` label. Unlabeled torrents, `library-seed`, other labels and anything finished or seeding are never touched.

A torrent is **stalled** when its state is Downloading, it moves under 1 KiB/s, and it has not downloaded for `STUCK_AFTER_MIN` minutes (default 20; a `time_since_download` of -1 counts only once the torrent has been active that long). The ladder, per stalled torrent:

1. Force a reannounce and move it to the top of the queue.
2. `STUCK_AFTER_MIN` later, if still stalled: pause, then resume.
Every stalled torrent is diagnosed first from what Deluge reports, and `GET /stuck-downloads`, the dry-run lines and the digest carry the diagnosis. A release is removed only when it could never complete.

What Deluge reports (from `deluge/core/torrentmanager.py` `on_alert_tracker_*`, `deluge/core/torrent.py`; 2.1.1 is identical to develop):

| Field | Values | Meaning here |
| --- | --- | --- |
| `tracker_status` | `Announce OK` | tracker working |
| | `Warning: <msg>` | tracker answered with a warning: working, the text stays on the row |
| | `''` or `Announce Sent` | not announced yet: no conclusion, no tracker report, no never-complete clock |
| | `Error: <msg>` | set only when no endpoint of that tracker works. `torrent_is_unregistered` is asked first (unregistered: left to the unregistered sweep), otherwise tracker error: reannounce, never blocklisted. One report per host, only after that host was in `Error:` on 2 passes in a row |
| | anything else | no conclusion, logged once |
| `total_seeds` | tracker `num_complete`, -1 unknown | 0 (not -1) is required for never-complete |
| `pieces` (`_get_pieces_info`) | per piece 3 done, 2 downloading, 1 a connected peer has it, 0 no connected peer has it; none when seeding or no metadata | read per hash, only for stalled candidates with 0 seeds; only the count of state-0 pieces is kept |

Diagnoses: unregistered, tracker error, pending, local (tracker working and seeds reported, or every missing piece is at a peer: uncap, reannounce, restart, notify once, never blocklisted), unknown swarm (seeds -1 or pieces unreadable: reannounce only) and **never complete** (tracker working, `total_seeds == 0` and at least one state-0 piece, on every pass for the whole `STUCK_GIVE_UP_HOURS` window; any other observation resets the window). Queued or paused time does not count.

3. After `STUCK_GIVE_UP_HOURS` (default 6) of never-complete, at any progress (there is no 95% exception, and manual grabs and season packs follow the same rule): if the release is in a Sonarr/Radarr queue, blocklist it there (`removeFromClient=false`, `blocklist=true`); remove the torrent and delete its files (the library guard still keeps files in library paths; this path alone skips the upload-based seed floor for a torrent that never finished, via `remove_torrent(never_finished_ok=True)`); then run `EpisodeSearch` / `MoviesSearch`. A torrent in no arr queue is still removed, and the digest says it was not blocklisted. One digest line per removal: name, percent, seeds, pieces no peer has, hours, blocklisted yes/no, files deleted or kept by the library guard. In `dry` mode: `[dry] would remove ...`, once per torrent.

A torrent that moves again starts over. The ladder is kept in `STUCK_STATE_PATH` (`/data/stuck_state.json`) in `on` mode so a restart does not reset it.

Upgrade-lane torrents are not on the ladder. Each one gets a per-torrent connection cap (`UPGRADE_MAX_CONNECTIONS`, default 10) so the 30 KiB/s upgrade torrents do not hold every peer slot; the cap is cleared when a superseded torrent is released.

`STUCK_AUTOMATION` is `off`, `dry` (the default, also for any other value) or `on`. `off` does nothing on the timer. `dry` logs and writes `stuck-downloads` activity lines only: no call is made that changes Deluge or the arr apps (the connection cap included), and no state is saved. `on` carries the actions out. Preview: `GET /stuck-downloads` (read-only; each torrent, its step and what the next pass would do).

## Deployment

Runs on Unraid at `/mnt/user/appdata/plex-automation`, on the `br0` macvlan network (external) at a static IP. `.env` lives only on the server and is gitignored — never commit real secrets.

- Add the Sonarr counterpart of the queue dupe pass, which never existed: `cleanup_sonarr_queue_dupes()`. Sonarr has the identical blind spot (`Deluge.GetItems()` → `GetTorrentsByLabel(TvCategory)`), so a throttled `sonarr-upgrade` torrent leaves `/api/v3/queue` the moment `handle_grab()` relabels it — and unlike Radarr, nothing was policing that population from either side. Candidate set is the Sonarr queue plus the in-flight throttled lane, identity for lane torrents coming from `/api/v3/history?downloadId=`. Identity is where the two services differ: a movie is one `movieId`, but a TV grab covers a *set* of episodes (single episode, multi-episode file, or season pack), so `seriesId` is not an identity — two different episodes of one series are not duplicates. Sonarr also emits one queue record *per episode*, so a season pack's records are folded back into a single candidate before anything is compared. A candidate is dropped only when its episode set is a **subset** of a keeper's, so the keeper delivers everything the loser would; keepers are chosen by coverage first (dropping a 10-episode pack to keep one higher-scoring episode inside it would leave nine episodes with nothing in flight), then custom-format score, then bytes already pulled. Straddling packs (`S01E01-05` vs `S01E04-10`) are both kept. Same safety properties as the Radarr pass: finished/seeding torrents are never touched, queue-record losers go through the queue API with `blocklist: False` (bulk endpoint, since a pack is many records), lane losers are relabeled `superseded` for `cleanup_superseded`, and each removal is individually wrapped.
